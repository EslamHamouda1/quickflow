# BUG-P8-002: Keyboard focus is lost (moves to `<body>`) after in-place actions such as toggling a task, habit, milestone or plan item
Status: closed (trial 1)
Owner: frontend-dev
Task: T105 (tasks.md) — UI code from T104 (accessibility pass: focus order) on the task, habit, learning, plan and dashboard components
Test case: TC-P8-FE-009   Story: US1, US2, US3, US4, US5   Phase: 8   Found in trial: 0

## Steps to reproduce   (exact curl / Playwright steps)
Playwright MCP `browser_run_code_unsafe` with `loops/loop-3-testing/outputs/playwright/p8-keyboard-actions.js` (keyboard only: Tab / Enter / Space), or by hand:
1. `page.goto('http://localhost:4200/tasks')`; press `Tab` until focus is on button "Mark as done: <task title>".
2. Press `Space`. The task becomes DONE (`curl -s http://localhost:8080/api/tasks/<id>` → `"status":"DONE"`).
3. Wait 800 ms and read `document.activeElement` with `browser_evaluate`: `() => document.activeElement === document.body`.
4. Repeat for the other in-place actions listed below.

## Expected
FR-034 / SC-010 / T104 ("focus order"): after an action that keeps the user on the same page, keyboard focus stays on the control that was used (the toggle, now labelled "Mark as not done: …" / "Undo today's completion: …"), or moves to a logical neighbour when the control disappears (e.g. the next row after archive / deactivate). A keyboard user must not be sent back to the start of the page (WCAG 2.1 SC 2.4.3 Focus Order).

## Actual
`document.activeElement` is `<body>` 800 ms after the action in 8 of 9 checked in-place actions; the next `Tab` starts again at "Skip to main content", so a keyboard user must tab through the header, navigation and toolbar again after every toggle (e.g. 58 stops on the Tasks page).

| Page | Action (keyboard) | Focus afterwards |
|---|---|---|
| Tasks | Space on "Mark as done: P8KB task" | BODY |
| Tasks | Enter on "Archive task: P8KB task edited" | BODY |
| Habits | Space on "Mark done for today: P8KB habit" | BODY |
| Habits | Enter on "Deactivate habit: P8KB habit edited" | BODY |
| Learning | Space on milestone checkbox "P8KB milestone 1" | BODY |
| Plans | Space on plan item checkbox "Task: P8KB plan item" | BODY |
| Dashboard | Space on "Mark done for today: P8KB dash habit" | BODY |
| Dashboard | Enter on "Complete task: P8KB due today" | BODY |
| Learning | Enter in "New milestone title for P8KB card" (add milestone) | stays in the input (correct) |

The actions themselves succeed (all 31 keyboard-only steps pass, verified with the API); only the focus position is lost. Dialog focus return (Esc / Cancel → opener) works correctly. No console errors.

## Suspected area
The focused button / checkbox element is destroyed and re-created when the item re-renders after the store update (e.g. `@if` switching between "Mark as done" and "Mark as not done" buttons, a new object identity for the row in `@for … track`, or the row moving between lists/sections such as active ↔ inactive habits). Keep the same element (change only its `aria-label` / `aria-pressed`), or restore focus after the update (e.g. focus the element with the same `data-id` + action in an `afterNextRender`), and move focus to the next row when the row leaves the list. Files: `features/tasks/task-item.component.ts`, `features/habits/habit-card.component.ts`, `features/learning/learning-card.component.ts`, `features/plans/*` (plan item checkbox), `features/dashboard/*` (habit checklist, due-today complete button).

## Fix (frontend-dev, trial 1)
**Root cause**: in-place actions set `[disabled]` on the used control while the request runs (browsers then drop focus to `<body>`), or remove the control's row (archive, deactivate, complete from "due today"), or re-create it elsewhere (a plan card moving from "Active" to "Completed"). Nothing put focus back.

**Files changed**
- `frontend/src/app/core/focus-restorer.ts` (new, root service): records the focused control (its row, list, position, owning `[data-id]` and accessible name) on `focusin`. When that control becomes disabled or removed (seen via `focusout` and a `MutationObserver`) and focus has fallen to `<body>`, it restores focus in this order: (1) the same control once it is enabled again; (2) the same control re-rendered elsewhere (same tag + accessible name + owning `data-id`); (3) the matching control of the next row (else the previous row) of the same list; (4) `<main id="main-content">` when the list is empty. It never moves focus that the user or a dialog has placed elsewhere, ignores dialogs, and does nothing when focus was lost by clicking a non-focusable area.
- `frontend/src/app/app.config.ts`: starts the service with `provideAppInitializer`.
