# BUG-P2-001: DELETE /api/tasks/{id} returns 406 (no CORS headers) when Accept is application/problem+json
Status: closed (trial 1)
Owner: backend-dev
Task: T025 (tasks.md)
Test case: TC-P2-BE-012   Story: US1   Phase: 2   Found in trial: 0

## Steps to reproduce   (exact curl / Playwright steps)
1. Create a task: `curl -s -X POST -H 'Content-Type: application/json' --data '{"title":"x"}' http://localhost:8080/api/tasks` → note `id`.
2. Delete it with the Accept header that the generated client (`TasksService.deleteTask`, built from the contract) sends:
   `curl -s -i -X DELETE -H 'Accept: application/problem+json' -H 'Origin: http://localhost:4200' http://localhost:8080/api/tasks/<id>`
3. Same for a missing id:
   `curl -s -i -X DELETE -H 'Accept: application/problem+json' -H 'Origin: http://localhost:4200' http://localhost:8080/api/tasks/999999`

## Expected
`deleteTask` per `contracts/openapi.yaml`: 204 (no body) for an existing task; 404 `application/problem+json` for a missing one. The 204 response has no body, so no representation needs to match `Accept`, and the 400/404 responses are declared as `application/problem+json`, so a client that accepts only `application/problem+json` must be served. 406 is not a documented status for this operation.

## Actual
Both requests return **406 Not Acceptable** and the task is **not deleted**:
```
HTTP/1.1 406
Accept: application/json
Content-Type: application/problem+json

{"detail":"Acceptable representations: [application/json].","instance":"/api/tasks/999999","status":406,"title":"Not Acceptable"}
```
The 406 response has no `Access-Control-Allow-Origin` header, so in the browser it shows up as a CORS error. With `Accept: application/json`, `*/*`, or `application/json, application/problem+json`, the result is 204 / 404 as expected.

The UI still works only because frontend-dev added the workaround `frontend/src/app/core/accept-header.interceptor.ts`, which widens the Accept header. Every future body-less operation (habit/card/plan deletes, `DELETE /api/habits/{id}/completions/{date}`) will hit the same problem. Curl results: `loops/loop-3-testing/outputs/phase-2-test-report.md`, rows BE-056 and BE-057.

## Suspected area
`backend/src/main/java/com/quickflow/task/TaskController.java`: class-level `@RequestMapping(produces = MediaType.APPLICATION_JSON_VALUE)` also applies to `deleteTask`, so content negotiation rejects `Accept: application/problem+json` before the handler runs. Possible fixes: give `@DeleteMapping` its own `produces` that also includes `application/problem+json` (or no `produces`), or add `application/problem+json` to the controller's `produces` list. Then confirm that 404/400 error responses for this request are problem+json with CORS headers.

## Fix (backend-dev, trial 1)
**Root cause**: the class-level `@RequestMapping(produces = "application/json")` on `TaskController` was inherited by `deleteTask`. Spring MVC's produces condition rejected `Accept: application/problem+json` while matching the handler, before the handler ran, so the response was 406. No handler was matched, so the CORS config never applied and the response had no `Access-Control-Allow-Origin` header.

**Files changed**
- `backend/src/main/java/com/quickflow/task/TaskController.java`: `@DeleteMapping(path = "/{id}", produces = {APPLICATION_JSON_VALUE, APPLICATION_PROBLEM_JSON_VALUE})`.
- `backend/src/test/java/com/quickflow/task/TaskControllerTest.java`: new test `deleteAcceptsProblemJsonOnly` (204 and 404 problem+json with `Accept: application/problem+json`).

`./mvnw verify` passes. The regenerated `backend/openapi/openapi.json` is unchanged; it differs from the previous file only in insignificant ordering, and the jq diff is empty. Future body-less endpoints (habit/card/plan deletes, completion delete) must declare the same `produces` pair.

**Verification** (server restarted):

Content-Type: application/problem+json
{"detail":"Task 999999 not found","instance":"/api/tasks/999999","status":404,"title":"Not Found"}
